# 解析层改动的噪声验收

## 为什么需要这套流程（30 秒背景）

这个项目把 PDF 解析成纯文本，喂给 LLM 做出版校对。**解析层留下的伪影会直接变成 LLM 报出来的假错误**——一个被栏宽切开的句子，LLM 会当成"多余空格"或"漏字"报给编辑。所以解析质量不是"排版好不好看"的问题，是产品输出正确性的问题。

本流程只覆盖 **A 类 PDF＝带文字层的 PDF**（`core/parser/native_pdf.py`）。扫描件走 OCR（B 类）是另一套装配逻辑，本流程的指标对它没有意义；`config` 里 `ocr="off"` 时无文字层的 PDF 会抛 `NoTextLayerError`，脚本整份跳过，属正常。

**这套流程存在的理由是一次真实事故**：分栏检测被改**对**之后，栏宽变窄，被栏宽顶回来的换行大量增加，数据库里同一份文档一次校对的问题数从 54 涨到 108。而当时的三条验收——单元测试全绿、全文本 diff 无回归、分栏验收线不变——**全是绿的**。那次没有人撒谎，错的是判据本身没有判别力。下面这套指标就是为了补上那个盲区。

## 两层验收

| | 工具 | 成本 | 看什么 | 何时必须跑 |
|---|---|---|---|---|
| **第 0 层** | `tools/parse_noise_metrics.py` | 零，确定性可复算 | 三个机械指标 | **每次改动，改前改后各一次** |
| **第 1 层** | `tools/issue_noise_report.py` | 要真跑一遍校对，耗 API 额度 | 数据库里 LLM 实际报了什么 | 第 0 层通过、且改动目的就是减少假错误时 |

第 0 层量的是"文本里还剩多少伪影"，第 1 层量的是"这些伪影有没有真的变成假错误"。第 0 层不过不要进第 1 层——白花额度。

## 第 0 层：机械指标

```bash
# 改动前，先存基线（--dump 顺带把全文本写出来，供事后 diff）
python -X utf8 tools/parse_noise_metrics.py --dump out/before

# 改动后
python -X utf8 tools/parse_noise_metrics.py --dump out/after

# 只跑某一份样本时给文件名子串
python -X utf8 tools/parse_noise_metrics.py 预览版
```

样本从 `samples/` 目录读。输出是每份文档一行，外加末尾合计行：

```
文档                                        句中换行   位置断行   括号错位     块数
```

三个指标都是"越小越好"，各自对应用户能看见的一个现象：

| 指标 | 口径 | 用户看到的现象 |
|---|---|---|
| **句中换行** | 按阅读顺序把一页的块用 `\n` 拼起来，数其中"前一个字符不是句末标点"的换行 | LLM 看到词中断行，报成漏字/多余空格 |
| **位置断行** | `source_location` 里含 `\n` 的块数 | 界面和 Excel 导出里"页码/位置"列断成两行 |
| **括号错位** | `《` 后直接跟空白，或 `数字 《 .` 这种形状 | 全角开括号墨迹偏移导致的字序错乱 |

**判读规则：只准你这次改动针对的那个指标降，另外两个不许变坏。** 不是"三个数加起来降了就行"——这三类噪声成因互相独立，一个降另一个涨说明你换了一种伪影，不是消除了伪影。

## 第 1 层：数据库产出

需要两个 `record_id`：一条**基线**（改动前跑出来的）和一条**待验收**（改动后跑出来的）。

**注意：`tools/run_proofread.py` 不写数据库**（它只 print，`--save-json` 也只存文件）。record 只能由 Streamlit 应用产生：

1. `streamlit run app.py`
2. 选任务 → 标准校对 → 上传 `samples/` 里那份文档 → 跑完
3. 到"历史记录"页，选择框里每条记录形如 `#53 · 文档名 · 时间`，`#` 后面就是 record_id
   （也可以直接查 `data/app.db` 的 `records` 表）

理想情况是改动**前**就先跑一条基线存着。如果忘了，只能改回旧代码重跑一次——这也是为什么第 0 层要先做：它零成本，能挡掉大部分不值得花额度的改动。

```bash
python -X utf8 tools/issue_noise_report.py 53 54       # 基线 53 vs 待验收 54
python -X utf8 tools/issue_noise_report.py 53 54 -v    # 顺带列出每类的具体条目
```

四个分类，判据写死在脚本里，每次复算完全一致：

| 分类 | 是什么 |
|---|---|
| **N1** | 括号错位导致的字序错乱 |
| **N2** | 位置描述断成两行（跨页对开版面一页印两个页码） |
| **N3长** | `original_text` ≥ 40 字：正文长段被栏宽切开，`_paragraphs.py` 的块级合并针对的就是这一类 |
| **N3短** | < 40 字：表格/日历单元格里的两行标题。第一行没顶到栏最右，块级合并的"满行"闸门会正确放过它——**这是另一件事，要治得先有单元格概念** |

## 判读规则（全部反直觉，都是数据买来的）

**1. 绝不看 issue 总条数。** 同一份文档、同一模式连跑五次，总数在 35 / 71 / 83 / 54 之间波动。LLM 每次报什么本来就带随机性，单次总数没有判别力。只看上面四个分类。

**2. N3 必须拆长/短两栏看，合计数会骗人。** 实测：某次改动后 N3 合计从 35 涨到 53，看着像变坏了；拆开才看到 **N3长 27→8**，涨的全是一页活动日历上的 N3短。

**3. 某一栏变了，先去核对那一栏对应的块文本到底变没变，再下结论。** 接上一例：那一页的块在改动前后**逐字节相同**——数字变化纯粹来自"这次 LLM 恰好把它们逐条列了出来"。别急着回滚一个其实正确的改动。

**4. 一份改动只该让它针对的那一类降。** 和第 0 层同一条纪律。N3长 降了而 N1 涨了，是两件事，分开处理。

## 执行环境（Windows，照做即可）

- **所有解析相关脚本一律加 `-X utf8`**。不加且 stdout 被工具捕获时，Python 会按系统 ANSI 代码页（中文 Windows 是 GBK）编码**全部**输出，整份日志乱码。`chcp` 对这种情况无效。
- **涉及 OCR/PaddleX 且要把输出重定向到文件时，用 PowerShell 工具、先执行一次 `chcp 65001`，不要用 Bash 工具**。Git Bash（MinTTY）里执行 `chcp` 是静默失效的，看起来执行了实际什么也没发生。
- 这两条纯粹是终端显示/日志可读性问题，**不影响程序行为**，写进数据库的数据始终是正常 unicode。原理详见 `core/parser/CLAUDE.md`。

## 收工条件

- **只跑第 0 层就够**：改动只针对一类噪声，第 0 层里目标指标降、另两个纹丝不动，且改动不涉及段落/分栏结构。别为这种改动花 API 额度。
- **必须跑到第 1 层**：改动碰了分栏检测或段落合并（会改变换行分布），或者改动的初衷就是"减少 LLM 报的假错误"。
- **不算通过**：任何一个非目标指标变坏而没有解释；或第 1 层里某一栏变化但没去核对底层块文本变没变。

报告结论时贴原始输出（命令 + 未经转述的表格），不要只写"指标改善了"。

## 指标会过时，纪律不会

本文件有两层内容，寿命不同：

- **具体口径**（N1 的正则形状、N3 的 40 字阈值、三个指标的定义）绑定当前 `samples/` 这批文档的版式。换一批版式差异大的样本，这些判据可能失效甚至误判，届时要重新校准——改的是脚本里的常量和这一节的表格。
- **判读纪律**（改前改后各跑一次 / 只准目标指标降 / 绝不看总条数 / 合计会骗人必须拆栏 / 变化了先核对底层文本）与文档形状无关，是"对随机输出的系统怎么做回归验收"的一般方法，不随样本变化。

新样本进来时只需要重校准前一层。
