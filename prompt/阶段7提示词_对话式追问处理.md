## 模块定位

框架文档设计铁律第2条要求"结果必须分层，贯穿展示、追问、标记、导出全链路"——阶段8的导出已经让分层结果贯穿到了Excel，本阶段让分层结果贯穿到追问：用户对着某条已分层的问题卡追问"为什么建议这么改""这是不是误判"，系统带着**这条issue的原文上下文**调用LLM作答，**不重跑全文、不改变该条的分层/优先级/状态**（框架文档原话："回答仅影响该条，不重跑全文"）。

## 关键设计决策（实现前先对齐，不要臆测）

### 决策1：`context_snippet` 必须在 `persist_result` 落库时就地计算，不能等追问时才现算

**这是本阶段最容易走偏的一点，务必先理解原因。** `issues` 表只存 `page_location`（"第3页左栏"这种人类可读TEXT，阶段8的决策3已经说明这个字段不可靠不可解析）和 `original_text`，**没有存 `block_index` 这个整数**。而"原文前后文窗口"必须靠 `block_index` 去 `ParsedDocument.blocks` 里找相邻块的文本才能算出来——`ParsedDocument`（阶段2解析结果）只在 `core/workflow.py::run_standard_proofread()` 执行期间存在于内存里，函数返回后就没了，**追问发生的时刻（用户点问题卡的"追问"按钮，可能是校对完成几分钟后，中间隔了无数次Streamlit rerun）根本拿不到它**。

所以正确时机只有一个：`persist_result()` 把结果写库的**那一刻**，`parsed`（`ParsedDocument`）还在调用链上下文里，必须在这时候把每条issue的上下文窗口算好，存进已经存在但一直空着的 `context_snippet` 列（这列阶段1建表时就有，不用改表结构，不存在"老数据库缺列"的迁移问题）。之后追问时只需要从库里读这一列现成的文本，不用重新解析文档。

**由此必须做的连锁调整**（都在"本阶段任务"里展开）：`run_standard_proofread()` 的返回值要从单个 `ClassifiedResult` 改成 `(ClassifiedResult, ParsedDocument)` 元组，`persist_result()` 要新增一个 `parsed` 参数。这会牵动 `app.py` 和 `tests/test_stage6.py` 里对应的调用点——这是必要的连锁修改，不是本阶段范围蔓延，阶段4当年给 `proofread_chunk` 加 `parsed` 参数也是同一类"被下游真实数据结构逼出的调整"（CLAUDE.md 有先例）。

### 决策2：不新增 `reason`/`block_index` 等数据库列，追问的"依据"素材用现有列拼

`ClassifiedIssue` 在内存里还带 `reason`（LLM给出的判断依据一句话）、`llm_category`、`llm_confidence`、`original_suggestion`，但 `persist_result` 从阶段6起就没把这些写进 `issues` 表（`add_issue()` 没有对应参数）。本阶段**不新增数据库列去补全它们**——理由：`issues` 表结构是阶段1定的，且用户本机 `data/app.db` 已经有阶段6/8跑出来的真实数据，`CREATE TABLE IF NOT EXISTS` 不会给已存在的表追加新列，贸然加列会导致旧库上 `INSERT` 因列不存在而失败，需要额外写迁移逻辑，收益（追问回答能引用一句原始判断依据）远不够抵消这个复杂度。

追问要回答"为什么建议这么改"，靠现有 `issues` 表已有的 `original_text` + 本阶段新填的 `context_snippet` + `issue_type` + `layer` + `priority` + `suggestion` 组织成提示词，足够让LLM给出合理回答——`suggestion` 在存疑/引文两层本身已经包含了原始依据的转述（见阶段5 `_rule_quotation`/`_rule_factual` 的拼接逻辑），确定性错误/风格可选两层即使没有单独的reason，"原文+建议+问题类型"通常已经自解释。如果后续实际使用中发现回答质量明显因为缺 reason 受损，再考虑单独加列，不在本阶段预先做。

### 决策3：`answer_followup` 签名比占位多一个 `db_path=None`，且新增一个占位里没有的公开函数 `get_followup_history`

占位签名 `answer_followup(issue_id: int, question: str) -> str` 缺 `db_path`——和阶段8给 `export_issues_to_excel` 加 `db_path` 是同一个理由：内部要读写 `issues` 表，测试要能传临时库。

`get_followup_history(issue_id: int, db_path=None) -> list[dict]`（新增，占位没有）：`followup_history` 列存的是JSON字符串，`app.py` 要把历史追问渲染成对话气泡，不应该在 `app.py` 里现写 `json.loads` 去解析存储格式——存储格式是本模块的内部实现细节，理应由本模块提供解析好的结构给UI层用，这是关注点分离，不是随意扩展接口。

### 决策4：追问的"多轮"通过在 user_content 里拼历史文本实现，不改 `core/llm_client.py`

`core/llm_client.py::chat_completion(system_prompt, user_content)` 只接受一轮 system+user，没有多消息列表接口（阶段4验收冻结，不动）。同一条issue可能被追问多次，"多轮"效果通过**每次调用时把此前若干轮问答拼进 `user_content`** 实现（"历史追问：Q...A...Q...A... \n\n 本次追问：{question}"），而不是维护真正的多轮messages数组——用现有单轮接口就能做到，不需要改已验收模块的公开签名。

为控制token成本（呼应框架文档 T5"控制token成本"的要求，和分块阶段重叠区裁剪是同一类考量），拼历史时只取**最近 `config.FOLLOWUP_MAX_HISTORY_TURNS` 轮**，更早的追问历史仍然完整存在数据库里（不删减存储，只裁剪注入prompt的部分）。

### 决策5：UI 用 `st.chat_message` 纯展示历史 + `st.text_input`+按钮做输入，不用 `st.chat_input`

框架文档技术选型表写的是"`st.chat_message` / `st.chat_input`"，但 `st.chat_input` 有已知限制：不放在容器里时全局只能有一个实例；放进 `st.container`/`st.expander` 后才允许每个问题卡各有一个独立实例，具体行为以当前安装的Streamlit版本实测为准（阶段8已经踩过"AppTest对某些组件的支持程度和预期不一致，必须先跑一次实测脚本确认，不能凭记忆假设"这个坑，同样的谨慎用在这里）。而每篇文档可能有几十条issue，每条一个问题卡，如果 `st.chat_input` 在这个数量级下有渲染异常或Streamlit版本兼容问题，排查成本较高。

**改用更可控的组合**：历史问答仍然用 `st.chat_message("user")`/`st.chat_message("assistant")` 渲染出聊天气泡效果（满足"对话式"的界面要求，这个组件没有实例数量限制）；新问题的输入用普通 `st.text_input` + `st.button("发送", key=f"followup_submit_{issue_id}")`（每个key全局唯一，和现有采纳/拒绝按钮的key惯例一致），点击后调用 `answer_followup`、`st.rerun()`。如果实现时发现 `st.chat_input` 放进 `st.expander` 后其实工作良好，可以换回去，但要先跑一次真实页面验证（不要只跑通AppTest就当作验证充分——AppTest对这类组件的支持本身就不完全可信，阶段8已经验证过这一点）。

```python
def run_standard_proofread(file_path, progress_callback=None) -> tuple[ClassifiedResult, ParsedDocument]:
    """标准校对全链路：解析→分块→逐块LLM校对→结果分层。纯编排，不写库。

    返回 (ClassifiedResult, ParsedDocument) 而非阶段6原先的单个 ClassifiedResult——
    parsed 要传给 persist_result 用于计算 context_snippet（阶段7新增），
    ParsedDocument 只在本次调用链上存在，过后无法从数据库反查，必须在这里一并交出去。
    """
    parsed = parse_document(file_path)
    chunked = chunk_document(parsed)
    proofread_result = proofread_document(chunked, progress_callback=progress_callback)
    return classify_issues(proofread_result, parsed), parsed
```

内部为每条 `issue` 计算 `context_snippet`：`block_index is None`（未定位）时留 `None`；否则取窗口内 `parsed.blocks` 的文本拼接。新增一个模块内辅助函数：

```python
def _build_context_snippet(parsed: ParsedDocument, block_index: int) -> str:
    """取 block_index 前后各 config.FOLLOWUP_CONTEXT_WINDOW_BLOCKS 个block的文本拼接。

    可以直接用列表下标而不必线性扫描 block_index 字段：core/parser.py 无论走
    PDF原生/OCR/Word哪条通道，都是按阅读顺序把 ParsedBlock append 进 blocks 列表
    的同时用同一个递增计数器赋 block_index，所以 parsed.blocks[i].block_index == i
    恒成立（parser.py 里两处赋值逻辑都是"idx=0起步，每append一个block就idx+=1"）。
    """
    window = config.FOLLOWUP_CONTEXT_WINDOW_BLOCKS
    lo = max(0, block_index - window)
    hi = min(len(parsed.blocks) - 1, block_index + window)
    return "\n".join(b.text for b in parsed.blocks[lo:hi + 1])
```
调用处：`parsed is not None and issue.block_index is not None` 时才算，其余情况 `context_snippet=None`，传给 `add_issue(..., context_snippet=snippet)`。

**校验一下上面"block_index恒等于列表下标"的说法**：这是我读代码得出的结论（`core/parser.py` 里 `_parse_docx` 和PDF那条路径都是 `idx=0` 起步逐个append时 `idx+=1`），但你实现时如果发现有分支不满足这个假设，改用线性扫描 `next(b for b in parsed.blocks if b.block_index == block_index)` 兜底，不要在假设不成立的情况下静默给错误的上下文窗口。

### 5. `core/followup.py` 实现

```python
def answer_followup(issue_id: int, question: str, db_path=None) -> str:
    """针对指定问题条目的追问，携带其上下文调用 LLM 并返回回答，同时把本轮问答追加进该issue的追问历史。"""

def get_followup_history(issue_id: int, db_path=None) -> list[dict]:
    """返回该issue的追问历史，每轮为 {"question": str, "answer": str, "asked_at": ISO时间字符串}，无历史返回空列表。"""
```

内部逻辑：
1. `get_issue(issue_id, db_path=db_path)`，`None` 则 `raise ValueError(f"issue_id {issue_id} 不存在")`。
2. 解析该issue现有的 `followup_history`（`None` 视为 `[]`）。
3. 组装 system prompt（读取并填充 `prompt/followup_system.md` 模板，占位符替换同 `proofreader.py::_build_system_prompt` 的 `.replace()` 手法）。
4. 组装 user_content：取最近 `config.FOLLOWUP_MAX_HISTORY_TURNS` 轮历史（若有）格式化成"历史追问"文本 + 本次 `question`。
5. `chat_completion(system_prompt, user_content)` 拿到回答文本（纯自然语言，不是JSON，**不需要**阶段4那套JSON解析/校验/重试逻辑——追问回答本来就该是自由文本）。`LLMCallError` 不捕获，直接向上抛给调用方（`app.py` 已有处理 `LLMCallError` 的现成模式）。
6. 把 `{"question": question, "answer": answer, "asked_at": datetime.now().isoformat()}` 追加进历史列表，`json.dumps(..., ensure_ascii=False)` 后 `update_issue_followup()` 写回。
7. 返回 `answer`。
